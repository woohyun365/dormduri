# 법적 문서 게시 Runbook

공개 법적 문서(이용약관·개인정보 처리방침·개인정보 수집·이용 동의·만 14세 이상 확인)의 판을 백오피스에서 만들고, 승인하고,
철회하는 절차다. 규칙은 [legal basis](../policies/legal-basis.md)(`LB-R6` 판·`LB-R10` 고지·`LB-R11` 재동의)가 소유하고, 검사와
기록은 [백오피스 API](../../apps/backoffice-api/README.md) §8, 화면은 [백오피스 Web](../../apps/backoffice-web/README.md) §8,
공개 열람은 [사용자 API legal README](../../apps/api/src/legal/README.md)가 소유한다. 이 문서는 그 규칙을 운영자가 적용하는
순서만 적는다.

## 역할과 승인

- 백오피스는 운영자 컴퓨터의 `http://localhost:4300`으로 연다(접속은
  [백오피스 배포 runbook](../../infra/runbooks/release/backoffice-stage-deploy.md#운영자-접속)).
- 초안 편집·가져오기·게시 요청·철회 요청은 `LEGAL_EDITOR`, 승인·거절은 `LEGAL_APPROVER`가 한다. `OWNER`는 둘 다 한다.
- 승인자는 요청자와 다른 사람이다. 승인 권한 계정(`LEGAL_APPROVER`·`OWNER`인 활성 계정)이 요청자 하나뿐일 때만 요청자가 사유를
  적고 자기 승인한다. 자기 승인은 감사 행에 표시되고 `BackofficeSelfApproval` 경보가 울린다(`OA-R9`).
- 요청·결정은 passkey 재인증을 요구한다. 요청은 7일 뒤 만료되고, 거절·취소·만료된 게시 요청의 초안은 다시 편집 중이 된다.
- 문서 본문, 요청 사유, 결정 사유에 사용자 개인정보를 쓰지 않는다.

## 판을 고르는 법

| 하려는 일                                                                      | 고지 등급                | 시행일                                                                  |
| ------------------------------------------------------------------------------ | ------------------------ | ----------------------------------------------------------------------- |
| 운영 전 이미 공개한 옛 본문을 남김                                             | 이전 판 기록(HISTORICAL) | 그 본문의 적용 시작, 적용 끝은 승인일(KST) 전. 다른 기록과 겹치지 않음  |
| 그 문서의 첫 운영 판                                                           | 첫 게시(INITIAL)         | 승인일(KST)과 같거나 앞. 이전 판 기록이 있으면 마지막 적용 끝의 다음 날 |
| 그 밖의 변경                                                                   | 일반(GENERAL)            | 승인일(KST) + 7일부터                                                   |
| 약관의 불리한 변경, 처리방침의 수집 항목·목적 추가나 제3자 제공·국외 이전 추가 | 중대(SIGNIFICANT)        | 승인일(KST) + 30일부터                                                  |

- 이전 판 기록은 첫 게시 전에만 받는다. 첫 게시 뒤에는 일반·중대 판만 게시한다.
- 한 문서에 시행 예정 판은 하나다. 다른 날로 바꾸려면 그 판을 철회한 뒤 새로 요청한다. 철회하지 않은 판과 같은 시행일은 쓸 수 없다.
- 재동의 필요는 이용약관·개인정보 수집·이용 동의·만 14세 이상 확인에만 켜고, 이용약관의 중대 변경은 늘 켠다(`LB-R11`).
- 중대 판과 재동의 필요 판은 메일 받을 회원이 0명일 때만 승인된다(`LB-R10`: 중대 변경 안내 메일을 보낼 수단이 없음). 회원이 생긴
  뒤의 절차는 개정 안내 메일이 생길 때 이 절에 더한다.
- 처리방침에서 권리 침해 가능성이 낮은 사항(수탁자 목록 갱신 같은 것)은 일정 기간 모아 한 판으로 공지할 수 있다(`LB-R10`).

## 첫 게시

1. 저장소의 seed 판 목록을 가져오기 파일로 쓴다.

   ```sh
   node apps/api/prisma/seed-data/reference/export-legal-import-files.js --out <비어 있는 디렉터리>
   ```

   파일 이름은 seed 판 id(`<판 id>.import.json`, 이전 판 기록은 id에 `historical`)이다. 이미 있는 파일은 덮지 않는다.
   한 번에 보내는 초안 본문은 64 KiB까지다(지금 seed 문서는 가장 큰 것이 약 17 KB). 넘으면 화면이 보내지 않고 그 이유를
   보인다.

2. `법적 문서 > 초안`에서 `JSON 파일로 초안 만들기`로 파일 하나를 가져온다. 형식이 맞지 않으면 어느 칸인지 보이고 초안을 만들지
   않는다. 문서마다 이전 판 기록 파일을 첫 게시 파일보다 먼저 가져와 승인한다.
3. 초안 편집 화면에서 미리보기를 읽고 바꾸지 않은 채 `게시 승인 요청`을 누른다. 가져온 초안의 digest는 seed 판의 digest와 같다.
4. `법적 문서 > 게시 요청`에서 요청을 고른다. 앞 판이 없어 대조표 대신 본문 전체가 보인다. 본문 전체와 고지 등급·시행일을 읽고
   확인 표시를 한 뒤 승인한다. 검사가 지금 거절하면 승인이 닫히고 그 이유가 보인다.
5. `법적 문서 > 문서 판`에서 그 문서의 판이 `시행 중`(이전 판 기록은 `이전 판`)인지 본다.

## 개정

1. `문서 판`에서 시행 중 판을 열고 `이 판으로 새 초안 만들기`를 누른다. 고지 등급(일반·중대), 제안 시행일(기본값은 KST 오늘 + 7일·30일),
   변경 요약을 정한다. 저장소에 개정 초안 JSON이 있으면 `초안`에서 가져와도 된다. 변경 요약은 사용자 문서 화면에 그대로 보인다.
   주요 변경은 `주요 변경:` 뒤에 `…다.`로 끝나는 짧은 문장을 하나씩 쓴다. 화면은 그 문장마다 한 줄 목록으로 보인다.
2. 초안 편집 화면에서 제목·요약 항목·본문 section을 고친다. 표는 열·행을 더하고 지울 때 머리와 모든 행의 칸 수가 함께 맞춰진다.
   중대 변경 확인 줄에 해당하면 고지 등급을 중대로 바꾼다. `저장` 뒤 화면 아래의 조항 대조표에서 바뀐 조항만 바뀜·더함·지움으로
   보이는지 본다. 다른 운영자가 먼저 저장했으면 충돌 결과가 나오므로 새로 고친 뒤 다시 고친다.
3. 저장하지 않은 변경이 없을 때 `게시 승인 요청`을 누른다. 요청이 대기하는 동안 초안은 고칠 수 없다.
4. 승인자는 `게시 요청`에서 대조표, 변경 요약, 고지 등급, 시행일, 지금 검사 결과를 읽고 확인 표시 뒤 승인하거나 사유를 적어
   거절한다. 요청 뒤 초안이나 판이 바뀌었으면 결정이 충돌로 거절된다.
5. 승인하면 공지가 시작되고(DB 시각) 그 판은 `시행 예정`이다. 시행일 00:00 KST에 `시행 중`이 된다.

## 철회

- 시행일 전의 일반·중대 판만 철회한다. 시행된 판, 첫 게시, 이전 판 기록은 철회하지 않고 다음 개정으로 바꾼다.
- `문서 판`에서 시행 예정 판을 열고 `철회 요청`에 사유를 적는다. 승인자가 `게시 요청`에서 그 철회 요청을 승인하면 그 판은
  `철회`가 되고 공개 열람에서 빠진다. 철회는 되돌리지 않는다. 같은 내용이 다시 필요하면 새 초안으로 다시 요청한다.

## 마지막 성공본 확인

- 사용자 API는 요청마다 DB에서 게시 판을 읽고, 성공한 묶음을 process memory에 둔다. DB 읽기가 실패하면 그 묶음으로 답하고, 묶음도
  없으면 503 `LEGAL_DOCUMENTS_UNAVAILABLE`이다. 묶음은 승인 없이는 바뀌지 않으므로 그 사이 memory 응답도 맞는 판이다.
- 승인 뒤 공개 열람(`GET /api/legal/documents/:kind/page`)의 판 목록에 새 판이 시행 예정으로 보이는지 본다.
- `api_legal_document_reads_total`에서 `source="memory"`나 `outcome="unavailable"`이 늘면 DB 읽기가 실패하고 있다(DB 읽기가
  1.5초 안에 끝나지 않은 것도 실패, 오류 종류 `LegalDatabaseReadTimeout`). 10분 창에 하나라도 있으면 경보 `ApiLegalReadDegraded`
  (warning)가 Slack으로 온다. 같은 때의 API warn log 한 줄(실패 단계·kind·오류 code)로 원인을 보고, DB 쪽은
  [`infra/runbooks/`](../../infra/runbooks/)의 절차를 따른다.
- 사용자 Web은 `/privacy`·`/terms`가 API에서 받은 응답을 user host의 named volume(`dormduri-web_legal-last-success`)에 요청마다
  파일로 남긴다. API가 답하지 못하면(연결·3초 timeout·오류 상태) 그 파일을 '마지막으로 확인한 문서'(확인 시각)로 보이고, 파일이
  없으면 '문서를 불러오지 못했습니다'다. 파일로 답할 때마다 Web log 한 줄이 남는다.

  ```logql
  {service="web"} | json | eventName="web_legal_last_success"
  ```

  `action="served"`는 파일로 답한 요청(`documentKind`·`versionKey`·`checkedAt`), `action="write_failed"`는 응답을 파일로 남기지
  못한 요청이다. `errorCode`가 원인이다(`EACCES`·`EPERM` 권한, `ENOSPC`·`EDQUOT` 공간, `EROFS` 읽기 전용, `ENOENT`·`ENOTDIR`
  디렉터리 없음, 그 밖은 `OTHER`). Web 배포는 두 화면이 API 게시본일 때만 새 Web을 남긴다
  ([Legal 단계 배포](../../infra/runbooks/release/legal-stage-deploy.md)).

- 결정은 `backoffice_legal_decisions_total{kind, notice_class, decision}`과 감사 기록(대상 `법적 문서 초안`·`법적 문서 판`)에 남는다.
  월 점검에서 자기 승인 행과 사유를 본다.

## 확인 항목

- 첫 게시와 이전 판 기록은 본문 전체를, 개정은 조항 대조표를 읽고 승인했는가
- 시행일이 고지 등급의 하한을 지키고 재동의 필요가 `LB-R11`과 맞는가
- 승인한 판이 `문서 판`과 공개 열람에 같은 상태로 보이는가
- 자기 승인이면 사유가 있고 경보를 확인했는가
