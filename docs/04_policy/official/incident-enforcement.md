| 8   | 기타               | 위 카테고리에 해당하지 않는 위반                          | —                                |

### Report intake baseline

Report intake는 신고 원장을 생성하고 접수 사실을 기록하는 단계다. Intake만으로 `SeasonParticipant.hidden*`, `deactivatedAt`, 계정 정지, 채팅 archive 같은 제재 projection을 직접 변경하지 않는다. Exposure/action을 닫는 projection은 운영 검토, 시스템 rule, 관리자 결정이 있는 별도 decision/write owner가 수행한다.

| 항목      | 정책                                                                                                           |
| --------- | -------------------------------------------------------------------------------------------------------------- |
| 신고 사유 | 위 8개 카테고리 중 하나를 필수 선택. lifestyle mismatch는 `허위 프로필`의 경미/피드백 후보로 시작              |
| 신고 대상 | profile, match request note, chat thread/message, support/운영 사건 등 구현 owner가 허용한 target              |
| 중복 신고 | 동일 reporter/target/category/open case는 idempotent 처리 또는 기존 case에 누적                                |
| 접수 응답 | 접수 완료와 후속 검토 안내. 피신고인 조치 여부나 내부 위험도는 노출하지 않음                                   |
| 접수 알림 | 신고인에게 in-app receipt 가능. 피신고인에게는 제재/임시조치 decision 이후 필요한 범위만 고지                  |
| 즉시 효과 | 없음. 고위험 신고도 operator alert/protective review 후보일 뿐 intake command가 직접 숨김/정지를 수행하지 않음 |

### False report / disclaimer

신고 UI와 접수 API는 “고의 허위 신고나 악의적 반복 신고는 제재 대상이 될 수 있다”는 disclaimer를 제공한다. 다만 허위 여부는 단일 반려만으로 판단하지 않고 반복성, 조작된 증거, 명백한 악의, 운영 로그와의 충돌을 기준으로 검토한다.

| 상황                | 처리                                            |
| ------------------- | ----------------------------------------------- |
| 근거 부족/판단 불가 | 신고 반려 또는 추가 자료 요청. 신고자 제재 없음 |
| 비의도적 오해       | 안내/피드백. 신고자 제재 없음                   |
| 반복적 악의 신고    | 경고 또는 이용 제한 후보                        |
| 조작 증거 제출      | 중대 위반 후보. 운영 검토 후 제재               |

### Risk tier / operator alert candidate

`riskTier`는 신고 접수 후 운영 우선순위와 알림을 위한 내부 signal이다. 사용자-facing response나 notification payload에는 raw risk detail을 노출하지 않는다.

| risk tier | 예시                                           | 운영 효과                                |
| --------- | ---------------------------------------------- | ---------------------------------------- |
| `LOW`     | 기타/스팸/경미한 불일치                        | 일반 queue                               |
| `MEDIUM`  | 반복 신고, 개인정보 노출 의심, 혐오 표현       | 우선 검토 queue 후보                     |
| `HIGH`    | 협박/위협, 성희롱, 스토킹, 자해/신체 안전 우려 | operator alert 후보, 즉시 보호 조치 검토 |

Operator alert는 notification campaign이나 사용자 알림함이 아니라 운영자 확인을 요구하는 internal alert다. High-risk 신고 접수는 먼저 candidate event를 남기고, notification owner가 allowlist payload만 가진 `OperatorAlert` record/sink handoff로 materialize한다. MVP에서 사용자 알림함에 operator alert raw payload를 싣지 않는다.

## 제재 체계

### 경중 분류 기반 제재 사다리

위반의 경중에 따라 제재 사다리의 진입점이 다르다.

| 경중                | 진입 단계                                     | 에스컬레이션 | 해당 카테고리                                          |
| ------------------- | --------------------------------------------- | ------------ | ------------------------------------------------------ |
| **경미** (minor)    | 경고 → 콘텐츠 제한 → 일시정지(7일) → 영구정지 | 순차         | 스팸/광고, 허위 프로필(경미), 기타                     |
| **중대** (major)    | 콘텐츠 제한 → 일시정지(30일) → 영구정지       | 경고 건너뜀  | 혐오/차별(반복), 타인 개인정보 유포, 허위 프로필(중대) |
| **즉시** (critical) | 즉시 정지 → 영구정지                          | —            | 성희롱(심각), 협박/위협, 성별 사칭                     |

### 제재 조치 상세

| 단계            | 조치 내용                                     | 서비스 이용                    |
| --------------- | --------------------------------------------- | ------------------------------ |
| **경고**        | 알림 발송 + 위반 기록                         | 제한 없음                      |
| **콘텐츠 제한** | 해당 콘텐츠 숨김/초기화. 닉네임은 임시 대체   | 제한 없음 (해당 콘텐츠만 조치) |
| **일시정지**    | 서비스 이용 정지 (7일 또는 30일). 로그인 차단 | 전면 차단                      |
| **영구정지**    | 계정 영구 정지. 동일 이메일 재가입 차단       | 영구 차단                      |

### 허위 프로필 경미/중대 기준

| 구분     | 판별 기준                                         | 예시                                           |
| -------- | ------------------------------------------------- | ---------------------------------------------- |
| **경미** | 주관적·검증 불가 영역의 부정확/과장               | 청결도를 실제보다 높게, 취침시간을 다르게 기재 |
| **중대** | 객관적 사실의 의도적 허위 → 매칭 자격·안전에 영향 | 건물 배정 허위, 캠퍼스 허위 기재               |

근거: 생활패턴은 자기 신고 모델의 본질적 한계이며 면책 범위다 (service-boundary.md). 건물/캠퍼스는 학교 시스템과 대조하면 판별 가능하고, 매칭 참여 자격(access-eligibility.md) 자체를 속이는 행위다.

### 비의도적 불일치 대응 원칙

생활패턴 불일치 신고의 첫 대응은 피드백(프로필 업데이트 유도)이며, 이는 잠버릇 등 본인이 인지하지 못할 수 있는 필드의 비의도적 불일치를 고려한 것이다.

- 의도를 직접 판별할 수 없으므로, 에스컬레이션 단계(피드백 → 경고 → 제한)의 **행동 패턴**으로 대응한다.
- 첫 신고 시 피드백은 비의도적 케이스를 보호한다. 피드백 후 미수정 + 재신고 시 의도성을 추정하여 경고로 에스컬레이션한다.
- 본인 인지 불가능 필드(예: `sleepHabit`)는 UI에서 helperText로 회상을 유도하되, 정확한 응답을 보장할 수 없는 구조적 한계를 인정한다.

### 누적 기간

| 항목        | 정책                                    | 근거                                                                                                                        |
| ----------- | --------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| 누적 윈도우 | **3년**                                 | 신고 이력 보관 기간과 동기화 (data-retention.md #6)                                                                         |
| 리셋        | 3년 경과한 위반 기록은 파기 → 자연 리셋 | data-retention.md 파기 정책                                                                                                 |
| 시즌 리셋   | 하지 않음                               | 시즌 종료 시 건물 배정·북마크·재신청 제한은 초기화, 진행 중 매칭/대화는 터미널 전이. 운영 로그는 보존 (season-lifecycle.md) |

## 즉시 분리/정지 트리거

경고나 단계적 에스컬레이션 없이 즉시 조치하는 트리거다.

| 트리거                    | 조치                                | 근거                                          |
| ------------------------- | ----------------------------------- | --------------------------------------------- |
| 성적 괴롭힘/성희롱 (심각) | 즉시 정지 + 수사기관 협조 가능 고지 | 정보통신망법 §44조의7                         |
| 협박/위협 (신체적 안전)   | 즉시 정지 + 수사기관 협조 가능 고지 | 정보통신망법 §44조의7                         |
| 성별 사칭 확인            | 즉시 **영구**정지                   | 무관용 원칙 (service-boundary.md 대응 원칙 4) |
| 타인 민감정보 유출        | 즉시 정지 + 해당 콘텐츠 삭제        | community-safety.md 민감정보 정의 준용        |

"즉시"의 정의: 관리자가 신고를 확인한 시점에서 추가 경고 절차 없이 바로 정지 조치.

민감정보: 개인정보보호법 제23조상 민감정보(건강, 성생활 등) 또는 그에 준하는 사생활 침해 우려가 큰 정보 (community-safety.md 정의).

## 증거 판단 기준

| 증거 유형                                              | 우선순위  | 용도                                        |
| ------------------------------------------------------ | --------- | ------------------------------------------- |
| **서버 로그** (채팅 기록, 프로필 변경 이력, 접속 로그) | 1차 증거  | 판단의 주된 근거. 위변조 불가               |
| **사용자 제출** (스크린샷, 설명)                       | 보조 참고 | 맥락 파악용. 단독 근거로 불충분 (조작 가능) |
| **시스템 기록** (필터 차단 이력, 신고 이력)            | 보강 증거 | 반복성/누적 판단                            |

## 공개 영역 임시조치

정보통신망법 제44조의2에 따른 임시조치 기준이다.

### 적용 범위

| 영역                                             | 성격                               | 임시조치 적용                        |
| ------------------------------------------------ | ---------------------------------- | ------------------------------------ |
| 닉네임 / season profile `intro` / 매칭 요청 note | 공개 또는 상대에게 노출되는 텍스트 | **적용**                             |
| 채팅                                             | 비공개 (1:1)                       | **미적용** — 별도 운영 판단으로 대응 |

1:1 채팅은 "일반에게 공개된 정보"가 아니므로 정보통신망법 §44조의2의 임시조치 대상이 아니다. 별도 운영 판단(제재 사다리)으로 대응한다.

### 콘텐츠 상태 모델

```
ACTIVE ──(임시조치)──→ HIDDEN ──(이의 없음/30일)──→ DELETED
                          │
                          └──(이의 인정)──→ RESTORED (= ACTIVE)
```

| 상태       | 의미                    | 타인 노출 | 본인 노출         |
| ---------- | ----------------------- | --------- | ----------------- |
| `ACTIVE`   | 정상                    | O         | O                 |
| `HIDDEN`   | 임시조치 중 (접근 차단) | X         | O + 임시조치 안내 |
| `DELETED`  | 삭제 확정               | X         | X                 |
| `RESTORED` | 이의 인정, 복원         | O         | O                 |

임시조치 = **숨김(접근 차단)**이 원칙이다. 원본을 보존하여 이의 시 복원할 수 있도록 한다. 초기화(삭제)는 30일 이내 이의 없음 또는 제재 확정 시 실행한다.

닉네임의 경우 `HIDDEN` 시 임시 닉네임으로 대체한다 (community-safety.md 닉네임 제재 특칙).

### 임시조치 절차

1. 신고 접수 (사생활 침해/명예훼손 등 주장)
2. 관리자 확인 후 임시조치 실행 (해당 콘텐츠 `HIDDEN`)
3. 작성자(피신고인)에게 임시조치 사실 + 사유 + 이의 신청 방법 통보
4. 30일 이내 이의 없으면 삭제 확정 (`DELETED`)
5. 이의 시 → 재심 후 판단 (`RESTORED` 또는 `DELETED`)

배상책임 감면: 정보통신망법 §44조의2에 따라 임시조치를 실행한 서비스 제공자는 배상책임이 감경/면제된다.

### 이의 신청

| 시점             | 창구                                          |
| ---------------- | --------------------------------------------- |
| MVP (Sprint 7~)  | 운영 이메일 (임시조치 통보 시 안내)           |
| 추후 (Sprint 9~) | #79 문의하기 기능에 "이의 신청" 카테고리 추가 |

이의 신청 절차: 이의 접수 → 관리자 재심 → 7일 이내 결과 통보.

## 고지 원칙

### 신고인 고지

| 항목      | 정책                                                     |
| --------- | -------------------------------------------------------- |
| 고지 내용 | 처리 완료 사실 + 조치 수준 (경고/제한/정지 중 어느 수준) |

## 탈퇴 계정 신고 처리

가해자가 신고 접수 **전** 탈퇴한 경우의 대응 구조다.

| 시점                          | 데이터 상태                                                                                                                                | 대응                                                                                    |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------- |
| 탈퇴 유예 기간 중 (5일 이내)  | 계정 데이터 잔존                                                                                                                           | 신고 접수 시 파기 중단 → 분리 보관 전환                                                 |
| 유예 이후 ~ 채팅 archive 유지 | active 계정 식별 정보는 비식별화됨. 채팅 + retained identity anchor + 접속/운영 로그는 보존 정책에 따라 잔존 가능                          | `RetainedIdentity` 제한 조회와 접근 로그를 통해 신고/수사 협조 가능                     |
| 채팅 식별 연결 검토 시점 이후 | 메시지 본문은 기본 archive 유지 가능. 다만 사용자 식별 연결은 2년 기준으로 재검토하고, legal hold/신고/분쟁 사유가 없으면 식별 anchor 폐기 | 본문 자체의 증거성은 남을 수 있으나, 식별 복원은 보존 사유·승인·암호키가 있을 때만 가능 |
| 접속/운영 로그 보관 이후      | 별도 법령/정책상 보존 사유가 종료된 로그는 파기                                                                                            | retained identity·채팅 archive만으로 대응 가능한 범위로 제한                            |

법적 근거:

- 파기 중단 → 분리 보관: 개인정보보호법 제21조 단서 + 민법 제750조·제766조 (data-retention.md)
- 채팅 archive 기본 유지: 개인정보보호법 제15조 제1항 제1호 및 처리방침 고지. 고정 90일 파기가 아니라 계정 식별 정보와 메시지 본문을 분리하고, 식별 연결은 보존 사유·승인·접근 로그 기준으로 제한
- 접속 로그 1년 보관: 안전성 확보조치 기준

이 구조는 data-retention.md의 기본 무기한 archive + 탈퇴 시 식별 정보 비식별화 + 제한 retained identity vault 구조와 정합한다. 추가 보관이 필요한 경우에도 보존 사유와 접근 근거를 retained identity access log로 남긴다.

## legal.ts 금지행위 조항 초안

#147(Phase 1 정책 코드 반영)에서 legal.ts에 반영할 금지행위 목록이다.

### 금지행위 목록

1. 성적 수치심을 유발하는 언행
2. 신체적 안전을 위협하는 언행 (협박, 스토킹 등)
3. 타인의 동의 없는 개인정보 공개
4. 성별을 허위로 기재하여 서비스를 이용하는 행위
5. 건물 배정 등 중요 정보를 허위로 기재하는 행위
6. 특정 성적 지향·성별·인종·장애 등을 이유로 타인을 배제하는 표현
7. 원치 않는 반복적 연락 또는 상업적·광고성 행위
8. 서비스의 정상적 운영을 방해하는 행위

### 제재 문구 초안

> 회사는 금지행위의 경중에 따라 경고, 콘텐츠 제한, 일시정지, 영구정지 등의 조치를 취할 수 있으며, 형사 수준의 위반 행위에 대해서는 경고 없이 즉시 정지할 수 있습니다.

> 위반 행위에 대한 증거는 민법 제750조·제766조에 따른 손해배상 소멸시효(3년)를 고려하여 보관합니다.

## SeasonParticipant visibility projection boundary

신고/제재 owner는 신고 접수, 심사, 운영 결정, 증거 보관을 소유한다. `SeasonParticipant.hiddenByAdminAt/hiddenReasonCode/hiddenReasonDetail`는 그 원장이 아니라, review/system/admin decision 이후 season-participants가 public exposure와 신규 action을 빠르게 닫기 위해 소비하는 **participant-level current projection**이다.

| projection reason  | 의미                                                             | 비고                                              |
| ------------------ | ---------------------------------------------------------------- | ------------------------------------------------- |
| `POLICY_VIOLATION` | 확정된 정책 위반으로 public exposure/action을 닫음               | 신고 접수만으로 설정하지 않음                     |
| `SAFETY_REVIEW`    | 안전 검토 결과 또는 검토 중 운영 결정으로 exposure/action을 닫음 | social-safety 원장/hold model은 후속 owner가 소유 |
| `ADMIN_REQUEST`    | 운영자 수동 결정으로 닫음                                        | 운영 로그와 사유는 내부용                         |
| `OTHER`            | 위 taxonomy로 표현하기 어려운 예외적 운영 결정                   | user-facing payload에 raw detail을 노출하지 않음  |

User block은 viewer-specific relation이므로 participant-level hidden reason으로 저장하지 않는다. #196 구현에서 report/block/enforcement workflow가 커지면 `ParticipantVisibilityHold`/`ParticipantSafetyHold` 또는 동등한 active hold model을 social-safety owner가 도입하고, `SeasonParticipant.hidden*`는 그 결과를 반영하는 projection으로만 갱신한다.

## RRPD disclosure와 운영 증거 접근

신고/제재/분쟁/수사기관 협조에서 삭제 사용자의 nickname audit, season profile history, match history snapshot, chat message body 원문이 필요한 경우 일반 product API를 통해 복원하지 않는다. 해당 payload는 RRPD(`RetainedVaultObject`)로 분리 보관된 경우에만, 운영 disclosure workflow에서 `accessedBy`, `accessReason`, `approvalReference`, `purpose`를 요구하고 `RetentionAccessLog`를 남긴 뒤 제한적으로 복원할 수 있다.

운영자는 retained vault payload를 자유 조회할 수 없으며, 신고 건·제재 건·분쟁 대응·적법한 외부기관 요청처럼 목적과 승인 근거가 있는 경우에만 접근한다. 접근 로그는 payload 폐기 이후에도 감사 목적의 별도 보존 대상이며, user-facing 화면/소켓/cache에는 복원된 원문을 전달하지 않는다.
