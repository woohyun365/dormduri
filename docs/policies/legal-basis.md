# 법적 근거 정리

## 문서 범위

이 문서는 서비스에 적용되는 법령을 단일 참조 문서로 관리한다. 각 정책 문서가 개별적으로 법령을 인용하지 않고, 이 문서를 참조한다.

- 검증 근거는 본문의 법령 조항과 문서 하단 변경 이력으로 추적한다. 개인 분석 초안은 canonical policy의 근거 경로로 사용하지 않는다.

## 접속기록 규율 대상 구분

두 법령이 "접속 기록"이라는 유사한 용어를 사용하지만, 규율 대상이 다르다.

| 법령                                | 규율 대상                                       | 보관 기간                                  | 현재 서비스 적용                                        |
| ----------------------------------- | ----------------------------------------------- | ------------------------------------------ | ------------------------------------------------------- |
| 개인정보 안전성 확보조치 기준 제8조 | **관리자/취급자**의 개인정보처리시스템 접속기록 | 1년 (5만명 이상 또는 민감정보 처리 시 2년) | **적용** — 1년                                          |
| 통신비밀보호법 시행령 제41조        | **이용자**의 인터넷 로그기록/접속지 추적자료    | 3개월                                      | **유보** — 부가통신사업자 등록 시 적용. Sprint 9 재검토 |

`data-retention.md`의 "접속 로그 1년"은 안전성 확보조치 기준에 따른 **관리자 접속기록**이다. 이용자 로그기록(통신비밀보호법)은 채팅 기능 구현 및 부가통신사업자 등록 여부에 따라 Sprint 9에서 재검토한다.

## 보존 근거 우선순위 해석

정책 해석상 아래 순서가 일반 삭제보다 우선할 수 있다.

1. 적법한 legal hold / 수사기관 요청
2. 신고·제재·분쟁 대응을 위한 예외 보존
3. 접속 로그 등 별도 법령상 보존 의무
4. 일반 탈퇴 계정 삭제

즉, `seasonEndDate`나 일반 탈퇴 요청이 발생해도 **법적 보존/신고/분쟁 대응 근거가 있으면 해당 보존 사유가 우선**한다.

또한 접속 로그 보관은 retained identity나 채팅 보관과 같은 층으로 합치지 않고, 별도 법령상 보존 의무로 해석한다.

## RRPD retained vault의 법적 기준

`RetainedVaultObject`에 저장되는 nickname audit, season profile history, match history snapshot, chat message body 원문은 복원 가능한 제한 보존 개인정보(RRPD)다. 따라서 “익명정보”로 보지 않고, 개인정보보호법 제21조의 파기/분리 보관, 제29조의 안전조치, 제30조의 처리방침 공개 요구를 구현 기준으로 삼는다.

| 설계 기준           | 법적/운영 해석                                                                            | 코드/정책 반영                                                    |
| ------------------- | ----------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| 파기 또는 분리 보관 | 목적 달성 후 불필요한 개인정보는 파기하고, 보존 근거가 있으면 active 개인정보와 분리 관리 | hot row는 tombstone/minimized, 원문은 retained vault로 분리       |
| 접근자 최소화       | retained payload 복원은 일반 product application 기능이 아님                              | disclosure owner만 decrypt 가능, product read path import 금지    |
| 접속/접근 기록      | 개인정보처리시스템 접근과 retained payload disclosure는 책임추적성을 가져야 함            | `RetentionAccessLog`에 접근자, 사유, 승인 근거, 결과 기록         |
| 처리방침 공개       | 보유기간, 파기절차, 보존 근거, 보존 항목을 사용자가 확인할 수 있어야 함                   | data-retention 문서와 product/privacy notice에서 RRPD 범주를 설명 |
| 가명/익명 구분      | 서비스가 key/anchor를 보유해 복원 가능하면 익명정보가 아님                                | `DEIDENTIFIED` user-facing 상태와 RRPD internal payload를 분리    |

운영자가 RRPD를 복원할 때도 application/backoffice level에서 승인 근거와 접근 로그를 남겨야 하며, 일반 사용자-facing API, socket, cache, profile/history read model은 retained payload를 복원하지 않는다.

DB 계층에서는 최소 권한 원칙을 별도 credential로 보강한다. `app_runtime` role은 product 기능 수행에 필요한 일반 테이블 권한만 가지고 retained vault/identifier payload 테이블을 직접 읽거나 쓰지 않는다. `retention_worker`는 archive/disposal/review 처리에 필요한 권한을, `retention_disclosure`는 승인된 disclosure read와 `RetentionAccessLog` 기록 권한을 가진다. 이는 개인정보보호법 제28조의 접근자 최소화와 제29조의 접근권한 제한·안전조치 요구를 application guard 밖 DB layer에서도 fail-closed로 보강하기 위한 기준이다.

## Retained identity 제한 조회의 법적 기준

탈퇴 계정의 식별 복원 가능 정보는 active `User` / `UserDisplayIdentity` / current season profile에 남기지 않고 `RetainedIdentity` 제한 영역에 분리한다. 이 영역은 일반 운영자가 자유롭게 조회하는 고객정보 테이블이 아니라, 신고·분쟁·법적 보존·수사기관 협조처럼 보존 근거가 있는 경우에만 접근하는 별도 개인정보파일로 본다.

| 기준                  | 적용                                                                                                                          |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| 분리 저장·관리        | 개인정보보호법 제21조 단서와 표준 개인정보 보호지침 제11조 취지에 따라 active 사용자 데이터와 retained identity anchor를 분리 |
| 접근자 최소화         | 개인정보보호법 제28조에 따라 retained identity 접근자는 일반 운영자와 분리하고 최소 범위로 제한                               |
| 접근권한/접속기록     | 개인정보보호법 제29조 및 시행령 제30조에 따라 접근권한 제한, 처리내역 접속기록, 안전한 보관 필요                              |
| 처리방침 공개         | 개인정보보호법 제30조에 따라 보유기간, 파기절차, 예외 보존 근거와 보존 개인정보 항목을 공개                                   |
| 암호키 기반 임시 식별 | DB에 평문 식별자를 남기지 않고 별도 키가 있어야 복원 가능하게 하되, 키 관리·승인 사유·접근 로그가 함께 있어야 함              |

따라서 `emailHash`나 암호화 payload가 있더라도 이는 익명정보가 아니라 접근 제한·보존기간·파기/분리 절차가 필요한 개인정보 또는 가명정보로 취급한다.

### "다른 법령"의 범위

| 용어                        | 범위                                                                                                                         |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| 법률                        | 국회 제정 법률만                                                                                                             |
| **법령** (제21조 단서 원문) | 법률 + 대통령령(시행령) + 총리령·부령(시행규칙)                                                                              |
| 행정규칙                    | 고시, 훈령, 예규 등 — "법령"에 포함되는지 논란. 다만 법률에서 직접 위임한 고시(안전성 확보조치 기준 등)는 실질적 구속력 인정 |

| 근거                              | 성격      | 설명                                                                                                                   |

| 형사소송법 제184조                | 참고      | 증거 보전 청구 제도. 민간 사업자의 보관 의무를 직접 규정하지는 않으나, 수사 협조 차원에서 합리적 보관 기간 설정의 근거 |

**주의**: "내부 방침"은 제21조 단서의 "다른 법령"에 해당하지 않는다. 예외 보관의 근거는 반드시 법령 또는 처리방침 명시 동의여야 한다.
