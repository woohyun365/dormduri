# 운영자 접근 정책

## 1. 책임

이 문서는 백오피스(관리자 화면과 백오피스 API)를 쓰는 운영자의 계정 발급, 인증, session, 재인증, 잠금, 권한 회수,
접속기록에 남길 내용과 접속기록 점검을 소유한다.

- 접속기록·권한 내역의 보존 기간과 파기: [data-retention.md DR-R5](./data-retention.md)(관리자 감사 3년),
  [data-retention.md DR-R6](./data-retention.md)(끝난 인증 상태 7일), [data-retention.md DR-R4](./data-retention.md)(접속 로그)
- 법적 근거: [legal-basis.md LB-R7](./legal-basis.md)(접속기록), [legal-basis.md LB-R9](./legal-basis.md)(권한 내역)
- 사용자 서비스의 계정·로그인: [account-authentication.md](./account-authentication.md). 관리자 계정은 사용자 계정과
  분리하므로 그 문서의 규칙이 관리자 계정에 적용되지 않는다.
- 관리자 table의 DB 권한(grant 표)과 접속 credential: [Database operator scripts](../../infra/db/README.md#grant-표)
- 이 규칙을 지키는 code와 test 위치: [백오피스 API README](../../apps/backoffice-api/README.md)

근거는 개인정보의 안전성 확보조치 기준(제2026-9호) 제2조제3호(접속기록의 뜻), 제5조(접근 권한의 관리), 제6조(접근통제),
제8조(접속기록의 보관 및 점검)다.

## 2. 계정과 인증

1. **OA-R1** 관리자 계정은 사용자 계정(`User`)과 분리하고 운영자마다 따로 발급하며 공유하지 않는다(제5조 제4항).
2. **OA-R2** 로그인은 비밀번호와 passkey를 모두 통과해야 한다. TOTP나 복구 code로 들어온 session은 새 passkey 등록과
   로그아웃만 할 수 있고, 그런 로그인이 있을 때마다 경보를 낸다.
3. **OA-R3** 15분 동안 요청이 없으면 session을 끝내고, 로그인하고 8시간이 지나면 다시 로그인해야 한다(제6조 제4항).
   로그아웃·권한 회수·잠금·비활성화는 그 계정의 session을 바로 끝낸다.
4. **OA-R4** 게시·승인·권한 변경은 직전 5분 안에 passkey로 다시 인증해야 한다.
5. **OA-R5** 비밀번호나 2단계 인증을 연속 5번 틀리면 그 계정을 15분 잠그고 경보를 낸다(제5조 제6항). 계정이 없거나
   잠긴 경우도 같은 응답 문구를 쓴다.
6. **OA-R6** 업무가 바뀌거나 퇴직하면 그날 권한을 회수하고 계정을 비활성화한다(제5조 제2항). 계정은 지우지 않고 감사
   기록과의 연결을 유지한다. 비활성화하면 그 계정의 비밀번호 hash·passkey·TOTP·복구 code를 바로 지운다.

## 3. 접속기록과 점검

7. **OA-R7** 접속기록에는 계정, 시각, 접속 경로, 다룬 대상, 수행 업무, 결과를 남긴다(제2조제3호). 로그인·로그아웃·
   만료·잠금·재인증 같은 접속과 초대·요청·승인·거절·비활성화·점검 같은 행위, 권한 부여·회수 내역을 관리자 감사 한 곳에
   남긴다. 비밀번호·code·token·passkey 응답과 사용자 개인정보는 남기지 않는다. 백오피스는 SSM 포트 포워딩 안에서만 열려
   앱이 운영자 IP를 볼 수 없으므로, 접속지 정보는 SSM 세션 시작 기록(CloudTrail trail)이 남긴다. 감사 기록이 실패하면 그
   행동도 하지 않은 것으로 되돌린다.
8. **OA-R8** Owner가 월 1회 관리자 감사와 SSM 세션 시작 기록을 대조해 접속기록과 권한 내역을 점검하고, 점검한 사실을
   관리자 감사에 남긴다(제8조 제2항). 이 주기와 방법이 내부 관리계획의 점검 항목이다.

관리자 감사는 백오피스 API만 추가하고 아무 계정도 고칠 수 없다. 읽는 쪽은 백오피스 API, 정리 조건 열만 읽는 정리 작업, 사유·
metadata를 뺀 열만 읽는 사람 DB 조회 계정이고, 사람 DB 조회는 pgAudit가 남긴다. 보존이 끝난 행의 폐기와 비활성 계정 익명화는
백오피스 API의 정리 작업만 하며, 사용자 API의 credential은 관리자 기록에 닿지 않는다(위·변조 방지, 제8조 제3항). 감사
시각은 DB 시계만 쓴다. 백오피스 API에는 시각 열을 넣을 권한이 없다.

## 4. 권한 부여와 첫 계정

9. **OA-R9** 권한은 업무별로 정한 역할 묶음으로만 주고(제5조 제1항), 역할 부여·회수는 승인 요청을 요청자와 다른 운영자가
   결정한다. 그 종류를 승인할 권한을 가진 활성 계정이 요청자 하나뿐일 때만, 요청자가 passkey 재인증(OA-R4)과 사유 입력 뒤
   자기 요청을 승인할 수 있다. 이 승인은 관리자 감사에 자기 승인으로 표시하고 경보를 낸다. 승인 권한 계정은 결정할 때 세므로
   둘째 승인 계정이 생기면 그때부터 예외는 거부된다. 요청자는 자기 요청을 거절하지 않고 취소한다. 요청은 7일 안에 결정하지
   않으면 만료된다. 마지막 승인 계정의 승인 역할 회수와 그 계정의 비활성화는 거부한다. 승인 권한 역할을 가진 계정을
   비활성화해 승인 권한 계정이 요청자 하나만 남게 되면 비활성화를 거부한다. 그 역할은 먼저 승인 요청으로 회수한다(대상
   운영자도 결정할 수 있다). 그 밖의 비활성화는 OA-R6에 따라 바로 하고 그 계정의 역할을 함께 회수한다.
10. **OA-R10** 첫 owner 계정은 활성 관리자 계정이 하나도 없을 때만 SSM 일회성 명령(`bootstrap-owner`)으로 만든다. 명령은 15분
    동안 한 번 쓰는 등록 code를 내고, code는 hash로만 둔다. 이 owner 역할 부여는 관리자 감사에 system 행위자의 행으로
    남는다. 그 뒤 계정은 owner가 초대하고(초대 code도 15분 동안 한 번만 쓴다), 역할은 OA-R9의 승인 요청으로 준다.

## 5. RRPD 열람 승인

11. **OA-R11** 제한 보존 개인정보(RRPD, [data-retention.md](./data-retention.md#rrpd--retained-vault-용어))의 열람·반출·보존
    hold는 제한 권한(`admin:restricted:*`)으로만 하고, 이 권한은 지금 어느 역할에도 없다. 일반 관리자는 RRPD를 자유롭게
    조회하지 않는다. 열람은 건마다 아래 표의 사유와 근거 문서 번호(`approvalReference`)를 적은 요청을 OA-R9에 따라 승인한
    뒤 그 건의 대상만 한 번 연다. 1인 예외로 승인한 열람은 OA-R9의 표시·경보에 더해 OA-R8 점검에서 따로 확인한다. 공개·거부·
    폐기 결과는 모두 `RetentionAccessLog`에 남긴다(거부한 요청도 남긴다). 복원은 `retention_disclosure` DB 경계만 하며,
    백오피스 API의 권한(`backoffice_runtime`)으로는 RRPD table을 읽을 수 없다.

| 사유(`RetentionAccessReason`) | 목적                                  | 근거([legal-basis.md](./legal-basis.md) 행) | 근거 문서 번호    |
| ----------------------------- | ------------------------------------- | ------------------------------------------- | ----------------- |
| `LAW_ENFORCEMENT_REQUEST`     | 수사기관의 법령에 따른 자료 요청 대응 | 수사기관 협조                               | 요청 공문 번호    |
| `REPORT_REVIEW`               | 접수된 신고의 사실 확인               | 신고/제재 운영                              | 신고 id           |
| `ENFORCEMENT_REVIEW`          | 제재 결정과 이의 검토                 | 신고/제재 운영                              | 제재 id           |
| `DISPUTE_RESPONSE`            | 이용자 사이 또는 서비스와의 분쟁 대응 | 법적 보존 / 분쟁 대응 보존                  | 분쟁 접수 번호    |
| `SECURITY_AUDIT`              | 침해 의심과 안전조치 점검             | 탈퇴 계정 식별 anchor 및 RRPD 제한 조회     | 점검 기록 번호    |
| `RETENTION_EXPIRY_REVIEW`     | 보존 기간 만료 때 계속 보존·파기 판단 | 탈퇴 계정 식별 anchor 및 RRPD 제한 조회     | retention case id |

요청자는 제한 권한 역할을 받은 운영자이고, 승인자는 요청자와 다른 승인 권한 운영자다. 제한 권한 역할과 열람 화면·disclosure
API는 RRPD 열람 기능을 더하는 변경이 이 절을 지키도록 만든다. 그 전까지 어느 운영자도 백오피스로 RRPD를 열 수 없다.
