# SWE common criteria

[Review criteria](./README.md)의 `swe` 기준입니다. 제품 code·공유 contract와 그 test·설정의 동작·구조를 바꾸는 변경에
적용합니다. 모든 영역에 공통인 기준만 둡니다. 보안·개인정보, 동시성·transaction, 영역 고유 규칙은 영역 기준 문서가
소유합니다. Linter·typecheck가 판정하는 형식·언어 규칙과 함수 길이 같은 수치 임계는 두지 않습니다. 영역 기준 문서는 이 문서의
항목을 상속하고, 이 문서의 항목은 영역 문서를 골라도 자기 기본 severity로 그대로 적용됩니다.

각 항목의 지침·피함은 구현할 때 보는 보기이고, 나머지 줄은 리뷰할 때 보는 보기입니다. 적용 조건은 두 보기가 함께 씁니다.

### S1. 요구사항·intent·invariant 부합

- 질문: 변경이 요청·acceptance·invariant와 기록된 의도·결정을 충족하고, 요청 밖 동작을 더하지 않는가?
- 기본 severity: `high`
- 적용 조건: 동작·구조를 바꾸는 모든 code 변경
- 결함 패턴: acceptance 일부만 구현하고 완료로 보고함, 요청에 없는 동작·설정·refactor를 같은 변경에 섞음, invariant(금지 전이·불변 값)를 깨는 경로가 남음, 그럴듯하지만 기록된 의도·결정과 다른 해법을 고름
- PASS 근거: acceptance·invariant마다 그것을 보이는 test·runner 기록·source 위치가 있고, 의도·결정 기록이 있으면 해법이 그 기록과 맞는다는 대조가 있으며, diff의 모든 변경이 요청이나 acceptance 하나로 설명된다
- 지침: 착수 전에 acceptance·invariant와, 있으면 의도·결정 기록을 목록으로 만들고 변경마다 어느 항목을 위한 것인지 연결한다. 범위를 바꿔야 하면 구현 전에 요청자와 정한다
- 피함: 요청 밖 개선을 같은 변경에 넣기, acceptance를 구현에 맞춰 줄이기, invariant 위반을 후속 작업으로 미루고 완료로 보고하기

### S2. 제품 정책 부합

- 질문: 바뀐 동작이 그 도메인의 정책 원본 규칙과 같은가? 다르면 정책을 먼저 바꿨는가?
- 기본 severity: `high`
- 적용 조건: 권한·상태 전이·기한·보존·공개 범위·사용자 문구처럼 정책 원본이 정한 규칙에 닿는 변경
- 결함 패턴: 정책이 정한 상태·기한·공개 범위와 다른 값을 code에 씀, 화면 문구나 오류 의미가 정책과 다름, 정책 변경 없이 code가 먼저 다른 규칙을 구현함
- PASS 근거: 바뀐 동작이 인용하는 정책 규칙과 그 규칙을 검사하는 test가 있다. 정책을 바꿨다면 그 변경이 같은 변경이나 선행 변경에 있다
- 지침: 구현 전에 정책 원본에서 바뀌는 동작의 규칙을 찾아 acceptance와 test에 인용한다. 정책과 다르게 해야 하면 정책 원본을 먼저 고친다
- 피함: 정책 원본 대신 기존 code나 화면을 규칙의 근거로 쓰기, 정책과 다른 동작을 임시 예외로 merge하기

### S3. 정확성과 오류 경로

- 질문: 경계값·빈 값·실패 경로에서 기대 동작을 하고, 오류가 삼켜지지 않고 의미에 맞게 전파·정리되는가?
- 기본 severity: `medium`
- 적용 조건: 분기·반복·변환·외부 호출·자원 획득을 바꾸는 code
- 결함 패턴: 경계(0·빈 목록·최댓값)에서 한 칸 어긋남, 빈 값을 정상 값처럼 진행함, 빈 catch·기본값 반환으로 실패를 성공처럼 보임, 실패 경로에서 자원·잠금·임시 상태를 정리하지 않음, 서로 다른 실패를 같은 오류 의미로 뭉침
- PASS 근거: 경계값과 실패 경로를 각각 실행하는 test가 있고, 오류가 호출자에게 구분되는 의미로 전달되는 위치가 보인다
- 지침: 입력의 경계와 실패 경로를 먼저 열거하고 각각의 기대 결과를 정한다. 오류는 처리할 수 있는 층에서 처리하고, 아니면 의미를 보존해 전파한다
- 피함: 오류를 삼키거나 log만 남기고 진행하기, 실패를 정상처럼 보이게 하는 기본값 반환, 정리 code를 성공 경로에만 두기

### S4. 책임 경계와 결합도

- 질문: 변경이 기존 owner·module 경계 안에 있고, 호출부 없는 추상화·경계 우회를 들이지 않는가?
- 기본 severity: `medium`
- 적용 조건: module·파일 구조, 의존 방향, 공용 utility·추상화를 바꾸거나 더하는 변경
- 결함 패턴: 다른 owner의 내부 구현·저장소를 직접 호출함, 호출부 하나뿐인 interface·class 계층이나 미래 확장용 layer를 만듦, 여러 책임을 한 파일에 모음, 호출부 확인 없이 code를 지우거나 남김
- PASS 근거: 새·바뀐 의존이 공개 경계(public contract·export)만 지나고, 새 추상화마다 현재 호출부나 필요 근거가 있으며, 의존 방향 검사가 있으면 통과한다
- 지침: 기존 owner·utility·pattern을 먼저 찾아 재사용하고 새 code는 그 책임을 가진 owner 안에 둔다. 다른 owner와는 공개 contract로만 연결한다. 정리·삭제는 호출부를 검색으로 확인한 뒤 한다
- 피함: 호출부 없는 추상화와 확장 지점, catch-all utility, 다른 owner 내부로의 직접 접근, 설계 원칙 이름을 근거로 계층 늘리기

### S5. 계약 호환성

- 질문: 공개 interface 변경이 모든 소비자와 같은 변경에서 맞춰지거나 호환 경로를 갖는가?
- 기본 severity: `medium`
- 적용 조건: HTTP·message schema, 공유 type·schema, export, CLI option, 설정 key, 저장 형식처럼 다른 module·process가 소비하는 interface의 변경
- 결함 패턴: 필드 이름·필수 여부·의미를 바꾸고 일부 소비자를 고치지 않음, 오류 code·status 의미를 말없이 바꿈, 내부 type을 공개 interface로 노출함, 저장된 이전 형식을 읽지 못함
- PASS 근거: 바뀐 interface의 소비자 목록(재현 가능한 검색)과 각 소비자의 수정 또는 호환 경로가 있고, producer·consumer test가 같은 schema를 쓴다
- 지침: 공개 interface를 바꾸기 전에 소비자를 검색으로 모두 찾는다. 같은 변경에서 모두 맞추고, 그럴 수 없으면 이전 형식을 함께 받는 호환 경로와 제거 조건을 둔다
- 피함: 소비자 검색 없는 공개 interface 변경, 이름을 유지한 채 의미만 바꾸기, 내부 저장 형식·DTO를 그대로 공개하기

### S6. 보호 test

- 질문: 바뀐 동작을 가장 가까운 layer의 test가 직접 보호하고, 결함 입력에서 실패하는가?
- 기본 severity: `medium`
- 적용 조건: 동작·거부 조건·계약을 바꾸는 code 변경과 결함 수정
- 결함 패턴: 정상 경로만 test해 실패·거부 경로가 무보호, 수정 전에도 통과하는 test, assertion이 구현을 그대로 복제함, mock이 실제 경계를 대신해 결함을 가림, 보호 없이 정리한 code에서 동작이 바뀜
- PASS 근거: 바뀐 동작마다 test 위치가 있고, 수정 전 실패 기록(RED)이 의도한 사유로 실패하며 수정 뒤 통과한다
- 지침: 결함 수정과 동작 변경은 먼저 실패하는 test를 쓰고 의도한 사유로 실패하는지 본 뒤 고친다. Test는 동작을 판정하는 가장 가까운 layer에 두고 실패·거부 경로를 포함한다. 보호되지 않은 code를 정리할 때는 회귀 test를 먼저 둔다
- 피함: 구현 뒤 통과하도록 맞춘 test만 두기, snapshot·mock으로 실제 판정을 대신하기, 실패하는 test를 skip하고 완료로 보고하기

### S7. dependency 도입과 version 의존 동작

- 질문: 새 dependency가 명시 요청과 정책 근거를 갖고 기존 utility로 대신할 수 없는가? version에 따라 동작이 다른 API는 쓰는 version의 공식 원천으로 확인했는가?
- 기본 severity: `medium`
- 적용 조건: 새 package·library·외부 service의 추가와 기존 dependency의 대체, version에 따라 동작이 다른 framework·library·provider API에 새로 기대거나 그 사용법을 바꾸는 변경
- 결함 패턴: 요청 없이 package를 추가함, 기존 utility나 표준 library로 충분한 기능에 dependency를 들임, 같은 역할의 dependency가 둘이 됨, license·유지보수 상태·dependency 정책 확인 없이 추가함, 쓰는 version을 확인하지 않고 기억이나 다른 version 문서의 API·option·기본값을 씀(없는 API·field 포함)
- PASS 근거: dependency를 요청한 기록, 기존 utility로 대신할 수 없는 이유, dependency 정책 확인 결과가 변경 설명에 있다. version 의존 동작은 lockfile의 version과 그 version 공식 문서를 대조한 기록이 있다
- 지침: 새 dependency는 명시 요청이 있을 때만 추가한다. 먼저 기존 utility·표준 library·이미 있는 dependency로 해결되는지 확인하고, 추가하면 version 고정과 정책 확인을 같은 변경에 둔다. version에 따라 동작이 다른 API는 lockfile의 current version과 그 version의 공식 원천으로 동작을 확인한다
- 피함: 편의를 위한 package 추가, 측정 근거 없이 유행하는 library 먼저 도입하기, 같은 역할 dependency 중복, 기억이나 다른 version 문서로 API를 추측하기

### S8. 측정 근거 있는 성능

- 질문: 성능 주장·최적화가 측정 가능한 bottleneck이나 budget에 연결되고, 알려진 hot path에서 복잡도를 악화시키지 않는가?
- 기본 severity: `low`
- 적용 조건: 성능을 주장하거나 최적화하는 변경, 반복·조회·직렬화가 많은 경로의 알고리즘 변경
- 결함 패턴: 측정 없이 cache·memoization·병렬화를 더해 복잡도와 오류 경로만 늘림, 반복 안에서 조회·할당을 되풀이해 입력 크기에 따라 비용이 급증함, 개선을 주장하지만 전후 측정이 없음
- PASS 근거: 최적화마다 대상 bottleneck이나 budget과 전후 측정값(환경 포함)이 있고, hot path의 복잡도 변화가 설명된다
- 지침: 최적화 전에 bottleneck을 측정하고 목표 budget을 정한다. Hot path를 바꾸면 입력 크기에 따른 비용을 확인한다
- 피함: 측정 없는 최적화, 근거 없는 고정 수치 임계를 규칙처럼 쓰기, 성능을 이유로 정확성을 먼저 희생하기

### S9. 가독성

- 질문: 읽는 사람이 한 번에 붙잡아야 할 맥락이 적고, code가 위에서 아래로 의도대로 읽히는가?
- 기본 severity: `low`
- 적용 조건: 동작·구조를 바꾸는 code
- 결함 패턴: 이름 없는 복잡한 조건과 의미 있는 숫자가 그대로 쓰임, 흐름을 따라 여러 위치를 오가야 이해됨, 중첩 조건식이 겹쳐 분기 결과를 읽기 어려움, 주석이 code를 되풀이하고 이유가 없음
- PASS 근거: 바뀐 code의 복잡한 조건·의미 있는 값에 뜻을 드러내는 이름이 있고, 한 함수가 위에서 아래로 한 흐름을 따르며, 주석이 있으면 code만으로 알 수 없는 이유를 적는다
- 지침: 복잡한 조건과 의미 있는 값에 이름을 붙이고 읽는 순서대로 흐름을 둔다. 중첩 조건은 이른 반환이나 이름 있는 조건으로 펼친다. 주석에는 이유를 쓴다
- 피함: 짧게 쓰려고 조건식 겹치기, 한 번만 쓰는 단순한 값까지 기계적으로 추출해 읽을 위치를 늘리기, code를 되풀이하는 주석

### S10. 예측 가능성

- 질문: 이름·parameter·반환 형태만 보고 동작과 부수효과를 예측할 수 있는가?
- 기본 severity: `medium`
- 적용 조건: 함수·method·module의 이름·signature·부수효과를 더하거나 바꾸는 변경
- 결함 패턴: 이름이 실제 책임과 다름, 이름에 드러나지 않는 부수효과(logging·전역 상태 변경·저장·외부 호출)가 숨음, 같은 이름이 위치에 따라 다른 동작을 함, 같은 종류의 함수가 서로 다른 반환 형태·오류 표현을 가짐
- PASS 근거: 바뀐 함수의 이름·signature가 동작과 부수효과를 드러내고, 같은 종류 함수가 같은 반환 형태·오류 표현을 쓰며, 부수효과가 호출부에서 보이는 위치에 있다
- 지침: 이름은 하는 일 전부를 드러내고 부수효과는 이름에 담거나 호출부로 꺼낸다. 같은 종류의 함수는 반환 형태와 오류 표현을 맞추고, 기존 이름과 같은 이름에는 같은 동작을 준다
- 피함: 읽기처럼 보이는 함수 안에서 쓰기, wrapper가 원본과 같은 이름으로 다른 동작을 하기, 함수마다 다른 반환 형태

### S11. 응집도와 중복 trade-off

- 질문: 함께 바뀌어야 하는 규칙·값은 한 곳에 있고, 앞으로 달라질 수 있는 code의 중복은 성급하게 공통화하지 않았는가?
- 기본 severity: `medium`
- 적용 조건: 규칙·상수·검증·변환 logic을 더하거나 옮기는 변경, 공통 함수·module을 만들거나 넓히는 변경
- 결함 패턴: 같은 규칙을 두 곳에 복제함, 함께 바뀌어야 하는 값(상수·검증 규칙·schema)이 흩어져 한쪽만 고치면 오류가 남, 앞으로 달라질 수 있는 code를 공통화해 호출부별 요구가 option·분기로 쌓임
- PASS 근거: 함께 바뀌어야 하는 규칙·값마다 원본 위치가 하나이고 다른 곳은 그것을 참조한다. 남긴 중복은 호출부의 요구가 다르게 바뀔 수 있다는 이유가 변경 설명이나 구조에서 보인다
- 지침: 함께 바뀌지 않으면 오류가 나는 규칙·값은 한 곳에 두고 참조한다. 비슷해 보여도 앞으로 다르게 바뀔 수 있는 code는 중복을 허용하고, 공통화는 같은 이유로 함께 바뀐다는 것이 확인될 때 한다
- 피함: 겉모양이 같다는 이유로 공통화하기, 공통 함수에 호출부별 option·flag를 계속 더하기, 원본 규칙을 복사해 고치기
