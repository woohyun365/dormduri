요청의 남용 방어, 사용자 입력의 주입 방어, 신고·차단·제재 동작을 바꾸는 변경에 적용합니다.

이 문서를 고르면 [`swe`](./swe.md)도 함께 고릅니다. 이 문서의 항목은 `swe` 항목을 상속하고 그보다 좁은 조건을 더 봅니다. 강화 관계는 P1 →

### P1. cookie 인증 상태 변경 요청의 cross-site 위조 방지

- 질문: cookie로 인증하는 상태 변경 요청을 server가 명시적으로 검사(출처 header나 위조 방지 token)해 cross-site 위조 요청을 거부하는가?
- 기본 severity: `high`
- 적용 조건: cookie 인증을 쓰는 상태 변경 요청(POST·PUT·PATCH·DELETE)의 진입점을 더하거나 바꾸는 변경
- 결함 패턴: SameSite 속성이나 전달 helper만으로 위조 방어가 된다고 봄, 출처나 위조 방지 token 검사 없이 상태 변경 요청을 받음, GET 요청으로 상태를 바꿈, 검사가 일부 진입점에만 있음
- PASS 근거: 상태 변경 진입점마다 출처(Origin·Fetch Metadata header 등)나 위조 방지 token을 검사하는 위치가 있고, 출처가 다르거나 token이 없는 위조 요청을 거부하는 negative test가 있다
- 지침: cookie 인증 상태 변경 요청은 server가 출처(Origin·Fetch Metadata header)를 명시적으로 검사해 다른 출처 요청을 거부하는 것을 기본으로 한다. 다른 출처의 form 제출을 받아야 하면 위조 방지 token을 검사한다. cookie 속성은 보조 방어로만 센다. 상태 변경은 GET으로 하지 않는다
- 피함: SameSite만 믿기, 일부 진입점만 검사하기, GET으로 상태 바꾸기

### P2. 서버 쪽 인가와 객체 단위 권한

- 질문: 요청자가 그 행동을 할 수 있는지와 대상 객체의 소유·관계를 server가 진입점마다 판정하고, 화면 표시나 client가 보낸 값에 기대지 않는가?
- 기본 severity: `high`
- 적용 조건: 요청자와 대상 객체의 권한을 판정하는 server 진입점·command를 더하거나 바꾸는 변경
- 결함 패턴: 화면에서 버튼·메뉴를 숨기는 것만으로 권한을 막음, 대상 id를 받는 진입점이 그 객체의 소유·관계를 확인하지 않아 다른 사용자의 id로 접근할 수 있음, 권한 판정이 진입점마다 흩어져 일부가 빠짐, 역할·운영자 권한을 client가 보낸 값으로 판정함
- PASS 근거: 진입점마다 공통 판정 위치와 대상 소유·관계 확인이 있고, 권한 없는 사용자의 요청과 다른 사용자의 id로 보낸 요청이 거부되는 negative test가 있다
- 지침: 권한은 server가 판정한다. 진입점 공통 판정으로 인증과 행동 허용을 확인하고, 대상 id를 받는 command는 그 객체의 소유·관계를 확인한다. 역할·운영자 권한은 server가 가진 값으로 판정하고, 화면 표시는 server가 알려 준 허용 결과를 따른다
- 피함: 화면에서 숨기기만 하기, 대상 소유 확인 없이 id로 조회·변경하기, client가 보낸 역할 값 믿기, 진입점마다 판정을 손으로 복제하기

### P3. 열거·추측·재전송·빈도 남용 방어

- 질문: 반복·추측·재전송할 수 있는 입력을 받는 진입점이 대상의 존재를 응답 차이로 드러내지 않고, 추측할 수 없는 식별자·token과 재전송 방어, instance 공통 빈도 제한을 갖는가?
- 기본 severity: `high`
- 적용 조건: 식별자·인증 시도·초대·신고처럼 반복·추측·재전송할 수 있는 입력을 받는 진입점
- 결함 패턴: 대상의 존재 여부를 응답 차이(상태 code·문구·응답 시간)로 드러냄, 추측할 수 있는 순차 id·token, 같은 요청을 재전송하면 상태가 두 번 바뀜, 시도 횟수·빈도 제한이 없음, 제한을 instance마다 따로 세어 instance가 늘면 한도가 풀림
- PASS 근거: 있는 대상과 없는 대상에 같은 응답을 내는 test, 같은 요청을 다시 보내도 상태가 한 번만 바뀌는 test, 한도를 넘는 시도가 거부되는 test가 있고, 빈도 제한을 instance가 함께 쓰는 저장소에서 센다
- 지침: 대상의 존재가 드러나는 응답(상태 code·문구·응답 시간)을 같게 맞추고, 밖에 보이는 식별자·token은 추측할 수 없는 값으로 만든다. 한 번만 일어나야 하는 요청은 재전송을 거부하거나 같은 결과를 돌려준다. 시도 빈도는 계정·대상별로 instance가 함께 쓰는 저장소에서 센다
- 피함: 대상 유무에 따라 다른 오류 문구, 순차 id·짧은 token 노출, instance가 둘 이상일 때 process 메모리에만 세는 빈도 제한

### P4. 주입·XSS·open redirect

- 질문: 사용자 입력을 query·명령·HTML·URL·redirect 대상으로 쓸 때 parameter binding·escape·허용 목록으로 다루는가?
- 기본 severity: `high`
- 적용 조건: 사용자 입력을 query·명령·HTML·URL·redirect 대상으로 쓰는 code
- 결함 패턴: 문자열 연결로 query·명령을 만듦, 사용자 입력을 escape·정제 없이 HTML로 넣음, redirect·link 대상 URL을 허용 목록·scheme 검사 없이 받음
- PASS 근거: query·명령이 parameter binding이나 인자 배열로 만들어지고, HTML 출력이 기본 escape나 정제를 거치며, redirect 대상의 허용 목록·scheme 검사가 외부 주소와 script scheme을 거부하는 test가 있다
- 지침: query와 명령은 parameter binding이나 인자 배열로 만들고 입력을 문자열로 잇지 않는다. HTML은 framework의 기본 escape를 쓰고, HTML을 꼭 넣어야 하면 정제를 거친다. redirect·link 대상은 같은 site의 상대 경로나 허용 목록의 주소만 받는다
- 피함: 입력을 이어 붙인 query·명령, 기본 escape를 우회한 HTML 삽입, 받은 URL로 그대로 redirect하기

### P5. 신고·차단·제재의 오탐과 이의

- 질문: 신고·차단·제재와 자동 판정이 오탐을 되돌릴 경로, 대상에게 알리는 이유와 이의 절차, 차단 뒤 정보·알림 차단, 신고자 신원 보호를 갖는가?
- 기본 severity: `medium`
- 적용 조건: 신고·차단·제재와 자동 판정의 동작을 더하거나 바꾸는 변경
- 결함 패턴: 자동 판정의 오탐을 되돌릴 경로가 없음, 제재 대상에게 이유와 이의 절차를 알리지 않음, 차단 뒤에도 상대에게 정보·알림이 감, 신고자 신원이 대상에게 드러남
- PASS 근거: 제재 해제·이의 처리 경로와 그 test, 차단 뒤 상대의 조회·알림이 막히는 test가 있고, 대상에게 보이는 응답에 신고자 정보가 없으며, 동작이 정책 원본과 맞는다
- 지침: 자동 판정에는 사람이 검토해 되돌릴 경로를 함께 둔다. 제재는 대상에게 이유와 이의 방법을 알린다. 차단은 조회·알림·초대 같은 모든 접점에 적용하고, 신고자 신원은 대상에게 보이지 않게 한다. 동작은 정책 원본을 따른다
- 피함: 되돌릴 수 없는 자동 제재, 이유 없는 제재, 일부 접점에만 적용한 차단, 신고자 노출
