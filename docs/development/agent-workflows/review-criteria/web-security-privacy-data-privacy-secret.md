# Web security-privacy data privacy and secret criteria

[Review criteria](./README.md)의 `web-security-privacy-data-privacy-secret` 기준입니다. 개인정보·비공개 필드·비밀값의 분류,
표시, 전달, 저장, 보존, 기록과 외부 처리자로의 전달을 바꾸는 변경에 적용합니다.

이 문서를 고르면 [`swe`](./swe.md)도 함께 고릅니다. 이 문서의 항목은 `swe` 항목을 상속하고 그보다 좁은 조건을 더 봅니다. 강화 관계는 P1~P5 →
[swe.md S2](./swe.md#s2-제품-정책-부합)입니다.
상속한 항목은 이 문서를 골라도 자기 기본 severity로 그대로 적용되고, 같은 결함이 두 항목에 함께 맞으면 기본
severity가 높은 항목으로 판정합니다. 이 문서의 항목을 상속하는 영역 문서는 그 문서 머리말에 적습니다.

각 항목의 지침·피함은 구현할 때 보는 보기이고, 나머지 줄은 리뷰할 때 보는 보기입니다. 적용 조건은 두 보기가 함께 씁니다.

### P1. 숨긴 신원·비공개 필드의 공개 범위 유지

- 질문: server가 숨긴 신원·비공개 필드를 client·BFF가 추론·재조회·cache·문구·URL·분석 event·log로 다시 드러내지 않는가?
- 기본 severity: `high`
- 적용 조건: 공개 범위가 제한된 신원·필드를 표시·전달·저장·기록하는 code
- 결함 패턴: 숨긴 값을 다른 API로 다시 조회함, 숨김 표시와 함께 원래 값을 응답·cache·URL에 남김, 문구나 개수로 숨긴 대상을 추론할 수 있게 함, 분석 event·log에 숨긴 값을 담음
- PASS 근거: 숨김 projection test(응답에 숨긴 필드가 없음)와 숨긴 대상을 다시 조회하지 않는다는 assertion이 있고, 분석 event·log의 필드 목록에 숨긴 값이 없다
- 지침: 공개 범위는 server 판정을 따르고 client·BFF는 숨긴 값을 받지도 다시 찾지도 않는다. 숨긴 대상은 필요한 최소 표시(익명 표기 등)만 쓴다
- 피함: 숨긴 값 재조회, 숨긴 값을 cache·URL·log에 저장하기, 개수·문구로 추론을 허용하기

### P2. 데이터 분류와 수집·전달 최소화

- 질문: 새로 수집·저장·전달하는 개인정보·민감 정보가 정책 원본의 분류(공개·비공개·민감)를 따르고, 목적에 필요한 필드만 수집·응답·전달하는가?
- 기본 severity: `high`
- 적용 조건: 개인정보·민감 정보를 새로 수집·저장·전달하거나 그 범위를 넓히는 변경
- 결함 패턴: 공개·비공개·민감 분류 없이 필드를 더함, 목적에 필요 없는 필드를 수집·응답·전달함, 정책 원본의 분류와 다른 공개 범위, data 흐름·공개 범위 표 없이 새 수신자에게 넘김
- PASS 근거: 새 필드마다 분류와 수집 목적이 정책 원본이나 변경 설명에 있고, data 흐름·공개 범위 표가 새 수신자를 포함하며, 응답·전달 payload에 목적 밖 필드가 없다는 test가 있다
- 지침: 필드를 더하기 전에 정책 원본의 분류로 공개 범위를 정하고, 목적에 필요한 필드만 수집한다. 새 수신자(화면·외부 서비스·분석)로 넘길 때는 data 흐름·공개 범위 표를 같은 변경에서 고친다
- 피함: 분류 없이 필드 더하기, 나중을 위해 미리 수집하기, 응답 객체를 통째로 넘기기

### P3. 보존 목적·기한·삭제·비식별

- 질문: 개인정보마다 보존 목적·기한이 있고, 기한이 지나거나 삭제 요청이 오면 모든 저장소에서 원래 값을 지우거나 다시 식별할 수 없게 처리하며, 그 처리의 감사 기록 owner가 있는가?
- 기본 severity: `high`
- 적용 조건: 개인정보의 보존 기한·삭제·익명화·동의 철회 동작을 더하거나 바꾸는 변경
- 결함 패턴: 보존 목적·기한 없이 저장함, 기한이 지난 data를 다음 요청이 올 때까지 남김, 삭제 요청·기한 뒤에도 표시만 바꾸고 원래 값을 남김, 삭제가 일부 저장소(사본·backup·검색 index·log)에 남음, 비식별 처리 뒤에도 다른 필드 조합으로 다시 식별됨, 삭제·열람 요청의 감사 기록 owner가 없음
- PASS 근거: 보존 기한이 정책 원본에 있고, 기한이 지난 data를 지우거나 비식별하는 실행 경로와 감사 기록이 있으며, 삭제 뒤 원래 값이 사본을 포함한 저장소에 없거나 비식별됐다는 test가 있다
- 지침: 보존 목적·기한은 정책 원본을 따르고, 기한이 지나면 요청을 기다리지 않고 지우거나 비식별한다. 삭제는 사본·검색 index·log까지 함께 다루고, 비식별은 남은 필드 조합으로 다시 식별되지 않는지 확인한다. 운영 data에 되돌릴 수 없는 삭제·익명화를 실행할 때는 사람이 대상 범위를 승인한다
- 피함: 기한 없는 저장, 기한이나 삭제 요청 뒤에도 표시만 바꾸고 원래 값 남기기, 원본만 지우고 사본 남기기

### P4. 비밀값과 log·telemetry 정제

- 질문: 비밀값이 저장소·image·계획·증거에 없고 실행 환경에서 주입되며, token·cookie·개인정보가 log·오류 보고·trace에 남지 않게 한 곳에서 정제하는가?
- 기본 severity: `high`
- 적용 조건: 비밀값·token·cookie를 다루거나 log·metric·trace·오류 보고를 더하거나 바꾸는 code·설정
- 결함 패턴: 비밀값을 저장소의 code·설정 파일, image, 계획·증거에 씀, token·cookie·개인정보를 log·오류 보고·trace 속성에 남김, 정제를 기록하는 곳마다 따로 해 빠진 곳이 생김, 외부 호출 payload를 정제 없이 기록함, 비밀값 교체 경로가 없음
- PASS 근거: 비밀값을 실행 환경 주입으로만 읽고 예시 설정에는 자리표시 값만 있으며, 공통 정제 경로를 거친 log·오류 보고 출력에 token·cookie·개인정보가 없다는 test가 있고, 비밀값 교체 절차가 있다
- 지침: 비밀값은 실행 환경에서 주입하고 저장소·image·문서에 값을 쓰지 않는다. log·오류 보고·trace는 한 곳의 정제 경로를 거치게 하고, 외부 호출 payload는 정제한 뒤 기록한다. 비밀값마다 교체 방법을 둔다
- 피함: 비밀값을 code·설정·문서에 쓰기, 기록하는 곳마다 따로 정제하기, 요청·응답 원문 기록하기

### P5. 외부 처리자와 법적 근거의 현재성

- 질문: 개인정보를 외부 provider로 보내기 전에 처리 지역·보존·운영자 접근과 위탁·국외 이전 고지를 확인하고, 법령·약관 근거를 공식 현재 원천으로 확인하는가?
- 기본 severity: `medium`
- 적용 조건: 외부 provider로 개인정보를 보내거나 법적 고지·동의 근거를 바꾸는 변경
- 결함 패턴: provider의 처리 지역·보존·운영자 접근을 확인하지 않고 개인정보를 보냄, 처리 위탁·국외 이전 고지가 없음, 법령·약관 근거를 공식 현재 원천 없이 기억으로 씀
- PASS 근거: provider의 처리 지역·보존·운영자 접근 확인과 고지 문구 변경이 변경 설명이나 정책 원본에 있고, 법령·약관 근거마다 확인 날짜가 있는 공식 원천이 있으며, 저장소에서 확인할 수 없는 값은 release 증거로 넘긴 기록이 있다
- 지침: 외부 provider로 개인정보를 보내기 전에 처리 지역·보존·운영자 접근을 확인하고 위탁·국외 이전 고지를 함께 고친다. 법령·약관 근거는 공식 현재 원천과 확인 날짜로 쓰고, 저장소에서 확인할 수 없는 계정·지역 값은 추측하지 않고 release 증거로 넘긴다
- 피함: 확인 없이 개인정보 보내기, 기억으로 쓴 법적 근거, 고지 없는 처리 위탁
