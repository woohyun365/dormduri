# Web BE transaction, concurrency, and idempotency criteria

[Review criteria](./README.md)의 `web-be-transaction-concurrency-idempotency` 기준입니다. Server command의 read-check-write 보호,
중복·재시도 요청의 처리, transaction과 외부 호출·event·메일 발송의 경계, 격리 수준·잠금·직렬화 실패 재시도를 더하거나 바꾸는
변경에 적용합니다.

이 문서를 고르면 [`swe`](./swe.md)도 함께 고릅니다. 이 문서의 항목은 `swe` 항목을 상속하고 그보다 좁은 조건을 더 봅니다. 강화 관계는 E1~E4 →
[swe.md S3](./swe.md#s3-정확성과-오류-경로)입니다.
상속한 항목은 이 문서를 골라도 자기 기본 severity로 그대로 적용되고, 같은 결함이 두 항목에 함께 맞으면 기본
severity가 높은 항목으로 판정합니다.

각 항목의 지침·피함은 구현할 때 보는 보기이고, 나머지 줄은 리뷰할 때 보는 보기입니다. 적용 조건은 두 보기가 함께 씁니다.

### E1. read-check-write 보호

- 질문: 읽은 값으로 판정한 뒤 쓰는 command에서 동시 요청이 같은 상태를 바꿀 수 있으면, 판정과 쓰기를 같은 transaction의 잠금·unique 제약·조건부 갱신으로 보호해 동시 종료 전이 두 개가 함께 성공하지 않는가?
- 기본 severity: `high`
- 적용 조건: 읽은 값으로 판정한 뒤 쓰는 command
- 결함 패턴: 확인과 쓰기 사이에 다른 요청이 끼어드는 경쟁(TOCTOU), 같은 transaction·lock·unique 제약 없이 판정함, 동시 종료 전이 두 개가 함께 성공함
- PASS 근거: 동시 요청이 같은 상태를 바꿀 수 있는 판정마다 보호 방식(같은 transaction 안의 잠금, unique 제약, 조건부 갱신, version 열)이 source에 있고, 실제 DB에 두 요청을 동시에 보내 하나만 성공하는 결정적 경쟁 test가 있다
- 지침: 동시 요청이 같은 상태를 바꿀 수 있는 판정은 확인과 쓰기를 한 transaction 안에서 잠그거나, unique 제약·조건부 갱신으로 DB가 마지막에 막게 한다. 한 번만 일어나야 하는 종료 전이는 동시 요청 test로 확인한다
- 피함: 동시 요청이 있는데 읽고 확인한 뒤 따로 쓰기, 동시 요청이 있는 판정을 진입점 검사만으로 막기, mock repository로 잠금·경합 판정을 대신하기

### E2. 중복·재시도 멱등성

- 질문: 재시도·중복 제출·재전송이 실제로 생기는 상태 변경을 멱등 key나 unique 제약 같은 중복 방지로 한 번만 처리하고, 멱등하지 않은 작업을 재시도하지 않으며, 재시도 경계가 없는 곳에는 멱등 key·분산 잠금을 들이지 않는가?
- 기본 severity: `medium`
- 적용 조건: 재시도·중복 제출·재전송될 수 있는 상태 변경
- 결함 패턴: 같은 요청 두 번을 두 번 처리함, 멱등하지 않은 작업을 재시도함, 실제 재시도 경계 없이 멱등 key·분산 lock을 들임
- PASS 근거: 재시도·중복이 생기는 경계(client 재시도, 재전송, 중복 제출, 작업 재실행)가 변경 설명에 있고, 그 경계에서 실제 DB에 같은 요청을 두 번 보내도 상태가 한 번만 바뀌는 test가 있으며, 멱등 key·분산 잠금을 둔 곳마다 그 경계가 있다
- 지침: 재시도·중복이 실제로 생기는 상태 변경만 멱등하게 만들고, unique 제약으로 중복이 막히면 멱등 key 없이 충분하다. 재시도는 멱등한 작업에만 둔다
- 피함: 재시도·중복이 생기는데 중복 방지 없이 두기, 멱등하지 않은 작업을 재시도하기, 재시도 경계가 없는 곳에 멱등 key·분산 잠금 들이기, mock repository로 중복 방지를 확인하기

### E3. 부수효과와 commit 경계

- 질문: 외부 호출·event·메일 같은 부수효과를 DB transaction 밖에서 commit 뒤에 내보내고, 부수효과가 실패할 때 outbox·재시도·보상 가운데 무엇으로 처리할지 정했는가?
- 기본 severity: `high`
- 적용 조건: transaction 안팎의 외부 호출·event·메일 발송을 더하거나 바꾸는 변경
- 결함 패턴: 외부 호출을 DB transaction 안에서 함, commit 전에 event·메일을 보내 rollback 뒤에도 나감, 부수효과 실패의 보상·outbox 판단이 없음
- PASS 근거: 부수효과마다 발송 시점(commit 뒤)과 실패 처리(outbox·재시도·보상, 놓쳐도 되면 그 이유)가 source나 변경 설명에 있고, rollback된 변경의 부수효과가 나가지 않는다는 test와 발송 실패 test가 있다
- 지침: 외부 호출은 DB transaction 밖에서 하고 event·메일은 commit 뒤에 보낸다. 놓치면 안 되는 부수효과는 같은 transaction에 발송 기록(outbox)을 남기고 발송 작업이 보내는 방식을 기본으로 하고, commit 뒤 바로 호출하면 실패를 재시도·보상으로 처리한다. 놓쳐도 되는 알림은 commit 뒤 바로 호출하고 실패를 재시도하거나 기록한다
- 피함: transaction 안에서 외부 호출하기, commit 전에 메일·event 보내기, 발송 실패를 처리하지 않고 버리기

### E4. 격리 수준·lock 선택과 재시도

- 질문: 격리 수준을 높이거나 잠금을 쓰는 곳에 막는 경쟁(근거)이 있고, 여러 자원을 잠그는 경로가 같은 순서를 쓰며, 직렬화 실패를 상한 있는 재시도로 처리하는가?
- 기본 severity: `medium`
- 적용 조건: 격리 수준·lock·직렬화 실패 재시도를 정하거나 바꾸는 변경
- 결함 패턴: 근거 없이 모든 transaction을 가장 높은 격리 수준으로 둠, 자원마다 lock 순서가 달라 deadlock이 남, 직렬화 실패를 재시도하지 않거나 상한 없이 재시도함
- PASS 근거: 격리 수준을 DB 기본값과 다르게 둔 곳마다 막는 경쟁(모든 transaction을 가장 높은 격리로 두면 그 근거)이 변경 설명이나 code 주석에 있고, 여러 자원을 잠그는 경로의 잠금 순서가 한 곳에 정해져 있으며, 직렬화 실패가 날 수 있는 transaction에는 재시도 횟수 상한과 그 test가 있다
- 지침: 격리 수준을 DB 기본값보다 높이는 곳은 막는 경쟁이 있는 판정으로 정하고, 높인 곳에는 상한 있는 직렬화 실패 재시도를 함께 둔다. 모든 transaction을 가장 높은 격리로 둘 때는 그 근거를 기록한다. 여러 자원을 잠그면 정해진 순서를 쓴다
- 피함: 근거 기록 없이 모든 transaction을 가장 높은 격리로 두기, 경로마다 다른 잠금 순서, 상한 없는 재시도
